# Deploying Lakeside Hotel

The production host runs PHP. It does not run Node, a queue worker, or a
scheduler, and this repository is arranged so that it does not need to.

## The live server, as it stands

| | |
| --- | --- |
| Domain | `lakesidehotelmw.net` (`198.251.89.101`) |
| Account / home | `lakesidehotel` · `/home/lakesidehotel` |
| Application | `/home/lakesidehotel/lakeside` (git checkout of `main`) |
| Document root | `/home/lakesidehotel/public_html` → symlink to `lakeside/public` |
| Previous docroot | `/home/lakesidehotel/public_html.bak` (kept for rollback) |
| Web PHP | 8.4.27, all required extensions present |
| CLI PHP | `php` is 8.1 — **always use `/opt/cpanel/ea-php83/root/usr/bin/php`** |
| Database | `lakesidehotel_hotel`, user `lakesidehotel_admin` |
| Media | `lakeside/public/bucket` — 162 files, 40 MB, generated by the seeders |

There is no Terminal feature in the Meridian theme, and `jupiter` only exposes one
at `/frontend/jupiter/terminal/index.html` inside a valid `cpsess…` session URL.
The `terminal` command is not in the account's feature list, so a tokenless URL
answers "Invalid Security Token".

## What the host has to provide

- PHP 8.3 or newer (production runs 8.4.27) with `pdo_mysql`, `gd`, `mbstring`,
  `openssl`, `fileinfo`, `exif`, and `tokenizer`.
  `gd` is not optional: every image the site shows is resized by the media
  library through it, so without `gd` the site comes up with no photographs.
- MySQL or MariaDB (production is MariaDB 10.11; the local database is MySQL 8,
  and nothing here is SQLite-only).
- Composer, or a machine that can run it before the files are uploaded.
- A writable `storage/`, `bootstrap/cache/`, and `public/bucket/`.

Node is deliberately absent from that list. `public/build` is committed, because
`@vite()` in `resources/views/app.blade.php` throws a
`ViteManifestNotFoundException` on every page when the compiled assets and their
manifest are missing, and the server has no `npm` to produce them.

## First deploy

```bash
git clone https://github.com/MotionPhix/lakeside-hotel.git
cd lakeside-hotel

composer install --no-dev --optimize-autoloader

cp .env.production.example .env
#   fill in APP_URL, the database, and the mailbox; then:
php artisan key:generate

php artisan migrate --force
```

`--force` is required: without it Artisan stops and asks for confirmation
because `APP_ENV=production`. The `booking_reference_sequences` table arrives
with these migrations and has to exist before the first reservation is taken.

### Content, once, on an empty database

```bash
php artisan db:seed --class=TeamSeeder --force
php artisan db:seed --class=SiteContentSeeder --force
php artisan db:seed --class=SiteSectionSeeder --force
php artisan db:seed --class=AccommodationSeeder --force
php artisan db:seed --class=ExperienceSeeder --force
php artisan db:seed --class=DiningPhotographySeeder --force
php artisan db:seed --class=MarketingSeeder --force
php artisan db:seed --class=HotelHouseRulesSeeder --force
```

Run these on a fresh database and not again afterwards: the seeders write the
hotel's copy over whatever is in the database, so re-running them after staff
have edited a page in the dashboard puts the original text back.

`TeamSeeder` reads `SEED_TEAM_PASSWORD` from `.env` for the five staff accounts.
Set it before seeding; without it production gets a random password per run and
prints it once, because the `password` the local fixtures use must not be what
guards a live dashboard. Nothing in this project can email a password reset yet
(see the mail section), so record that password.

**Do not run `php artisan db:seed` on its own.** `DatabaseSeeder` ends with
`GuestSeeder`, which creates forty-eight demonstration guests and then writes
real `Booking` rows for them. `GuestSeeder` now refuses to run when
`APP_ENV=production`, but the class list above is still the correct way to seed
a live site.

## Media

`public/bucket` is not in git. The 75 MB in it is output: resized copies of the
51 photographs the repository does ship in `database/seeders/photography`. The
content seeders above regenerate it, which is why they are run on the server
rather than copied over. The brand marks (`lakeside-wordmark.png`,
`lakeside-wordmark_v1.png`, `lakeside_hotel_logo.png`) are source files, not
output, and are tracked - each one is named in a `!` line in `.gitignore`,
because `public/bucket/*` is ignored wholesale.

Add every new brand mark to that un-ignore list in the same commit that starts
referencing it. `lakeside-wordmark_v1.png` was added to `SitePresenter` without
one, so it existed on the machine that made it and nowhere else: the live header
rendered a 168x48 empty box and 404'd the file until `544bcb9`.

If you would rather not have the server generate them, upload the local
`public/bucket` folder by SFTP into place before seeding. The paths are the same
either way.

## Finishing the deploy

```bash
php artisan config:cache
php artisan route:cache
php artisan view:cache
```

`storage:link` is not needed: `config/filesystems.php` writes media under
`public/bucket`, which the web server serves directly.

Then point the domain at the application's `public` directory. On this account
the docroot is a symlink, so the application stays outside the served tree and
`.env`, `vendor` and `database` are never reachable over HTTP:

```bash
cd /home/lakesidehotel
mkdir -p lakeside/public/.well-known
cp -a public_html/.well-known/. lakeside/public/.well-known/   # ACME challenges
mv public_html public_html.bak
ln -s /home/lakesidehotel/lakeside/public public_html
```

Keep `public_html.bak` until the site has answered a request, so a bad symlink is
one `mv` away from undone.

Nothing needs to stay running afterwards. No class implements `ShouldQueue`,
nothing dispatches a job, both booking emails go out through `Mail::to()->send()`
rather than being queued, and there is no `schedule()` call anywhere - so no
worker and no cron entry.

## Mail

Live as of 16 Nov 2026: `MAIL_MAILER=smtp`, `MAIL_SCHEME=smtps`,
`MAIL_HOST=mail.lakesidehotelmw.net`, `MAIL_PORT=465`, authenticating as the
`hello@lakesidehotelmw.net` mailbox and sending as
`reservations@lakesidehotelmw.net`. A message was accepted by the mail server
after `config:cache`, so the path from Laravel to the relay is proven. What that
does not prove is inbox placement - watch for a spam folder on the first real
booking.

To set this up on a fresh host: create the mailbox in cPanel (Email Accounts),
put the credentials in `.env`, and run `php artisan config:cache`. Send one test
booking and confirm the message arrives before telling anyone the site is live.

Two traps, both hit during the first deployment:

- Set the mailbox password through the cPanel UI. `uapi Email passwd_pop` with
  the password as an argument form-encodes it, so `+` arrives as a space and the
  mailbox ends up holding something other than what `.env` says. The symptom is
  a bare `535 Incorrect authentication data` on every send.
- `.env.example` ships `MAIL_FROM_NAME="${APP_NAME}"`. Appending a second
  `MAIL_FROM_NAME` leaves two lines for one key; the later one wins, so it works,
  but the duplicate is worth deleting.

Password resets go out through the same mailer, so staff cannot recover an
account until this is configured.

## Payments

With `PAYCHANGU_SECRET_KEY` blank the site is complete but takes no money
online: `isOnlinePaymentEnabled()` returns false, the booking page drops the Pay
Now option, and the server rejects a payment attempt anyway. Guests reserve and
settle at the hotel.

As of 16 Nov 2026 the live `.env` holds PayChangu **test** keys
(`sec-test-…`, webhook secret `nofuss_no_bash`), so the checkout path can be
exercised against the sandbox. Replace them with live keys before taking real
money.

Two things have to be true for online payment to appear, not one: the key has to
be set, and the **Online card payment** toggle under the dashboard's booking
settings has to be on. With a test key in place and the toggle on, a real guest
would reach a sandbox checkout - decide which of the two you want while the keys
are still test keys.

To turn payments on, set `PAYCHANGU_SECRET_KEY` and `PAYCHANGU_WEBHOOK_SECRET`,
then point the webhook in the PayChangu dashboard at:

```
https://<live-domain>/webhooks/paychangu
```

That route is outside CSRF (see `bootstrap/app.php`) and authenticates callers
with a signature over the raw body instead.

## Check it worked

- `https://<live-domain>/up` returns a healthy response.
- `/robots.txt` returns `text/plain` and a `Sitemap:` line built from `APP_URL`.
- `/sitemap.xml` returns `application/xml` and lists the room categories.
- The homepage shows photographs, not empty frames - that is `public/bucket`
  having been generated.
- Make a booking and confirm the guest receives the confirmation email.

## Shipping an update

```bash
git pull
composer install --no-dev --optimize-autoloader
php artisan migrate --force
php artisan config:cache && php artisan route:cache && php artisan view:cache
```

If the update touched anything under `resources/`, build on a machine with Node
(`npm run build`), commit `public/build` with it, and pull that. Do not leave the
committed manifest older than the source it was built from.

## HTTPS behind a proxy

`APP_URL` has to be the `https://` address. If TLS ends at a proxy or CDN,
make sure `X-Forwarded-Proto: https` reaches PHP - otherwise Laravel generates
`http://` URLs and the signed booking links in confirmation emails will not
open. Configure trusted proxies for the load balancer in that case.
